Decision brief / Multi-AgenticOS

De Hermes Agent a una torre de control multiagente.

Mapa verificable de control planes, runtimes, seguridad, observabilidad y patrones de dashboard. La recomendación preserva Hermes como núcleo y añade una capa operacional desacoplada.

Ruta prioritariaAgentTeams + Hermes Workers
Fuentes guardadas17 repositorios
Capas separadasControl · Telemetría · UI
ConfianzaAlta / Media

Decisiones principales

01
Conservar Hermes como execution plane

Memoria, skills, perfiles, gateway, herramientas, cron y delegación permanecen en el núcleo.

02
Validar AgentTeams antes de construir desde cero

Ya soporta Hermes como Worker, con recursos declarativos, dashboard, Matrix, MinIO y gateway de credenciales.

03
Usar un contrato neutral de eventos

OpenTelemetry/OpenInference primero; Langfuse, Phoenix u Opik como destinos intercambiables.

04
Separar control de observabilidad

Las trazas no reemplazan colas, cancelación, reintentos, workers, permisos ni checkpoints.

Señales críticas

Encaje directoAgentTeams documenta worker.defaultRuntime=hermes.
RestricciónHermes es Worker, no Manager, en el contrato actual.
UIOpenHands aporta el patrón más limpio de frontend desacoplado.
LicenciasPhoenix usa ELv2; Dify y varios proyectos combinan términos adicionales.
Arquitectura recomendada

Una capa de control sobre runtimes, no dentro de ellos.

La torre administra recursos, políticas y eventos. Los workers conservan su runtime y contexto especializado.

Fuentes primarias y límites.

Repositorios y documentación oficial consultados. Las afirmaciones comparativas de cada proyecto no se tratan como benchmarks independientes.

Limitaciones: las estrellas miden atención, no seguridad; no existe un benchmark común entre SDKs, runtimes y control planes; varias afirmaciones “production-ready” provienen de mantenedores. Confianza alta en funciones y estado documentados; media en la composición hasta completar el PoC.
